## Как запустить локальный сайт

Требования: Node.js 20+, npm.

Рекомендуемый способ — из корня проекта:

```powershell
npm install
npm run start:local:keep
```

или `start-local-keep.bat`.

Сайт: [http://127.0.0.1:43127/](http://127.0.0.1:43127/)

PostgreSQL: `127.0.0.1:55432`, база `tutoring_platform`.

`start:local:keep` **не перезаписывает** сид школы. Обычный `npm run start:local` применяет миграции и заново заполняет организацию `org_school_qa`. Для этой проверки используйте **keep**, чтобы не потерять уже накопленные данные.

Остановка: `Ctrl+C` в окне сервера.

Не подключайтесь к production / Timeweb. Не выполняйте `commit`, `push`, `deploy`, `db:seed`, сброс базы.

## Как открыть чек-лист

Откройте `docs/manual-audit/MANUAL_TEST_PLAN.md`. Идите по пунктам `MT-xxx` по порядку. ID функций из реестра (`DIR-STU-001` и т.д.) указаны рядом, чтобы при сбое можно было сослаться на конкретную функцию.

## Как отмечать результаты

У каждого пункта три варианта:

- **Пройдено**
- **Не пройдено** — коротко опишите, что увидели
- **Заблокировано** — укажите причину (нет данных, нет доступа, страница не открывается, опасно для существующих записей)

Можно копировать чек-лист в заметки или ставить отметки прямо в файле. Если правите файл в репозитории — это только документация; код приложения не трогайте.

Пометки в чек-листе:

- **Чтение** — можно выполнять на существующих данных без сохранения.
- **Изменяет данные** — запись в локальную БД; после проверки обновите страницу и убедитесь, что изменение осталось.
- **Опасно** — архивация, удаление, платежи, тарифы, зарплаты, массовые операции. Не выполняйте, если не готовы принять необратимое изменение существующих записей.

## Как сообщать о найденных проблемах

Пишите в чат агенту по шаблону:

```
ID пункта: MT-083
ID функции: PRS-FBK-004
Кабинет / страница: Пресса → Обратная связь → карточка отчёта
Роль: press
Что сделал: ...
Что ожидал: ...
Что получил: ...
Результат: Не пройдено
```

Можно группировать несколько пунктов. Не просите «просто починить всё» без ID: по номеру можно найти код, API и связанные сущности.

## Ограничения этой проверки

- Проверяется **локальный** сайт, не production.
- Ничего не исправлялось автоматически. Найденные в коде пробелы собраны в `KNOWN_GAPS.md`.
- Функция считается реализованной только если есть серверная логика и сохранение, а не только кнопка или маршрут.
- Статус «подтверждено тестами» означает: в репозитории есть соответствующие автоматические тесты. Это **не** доказательство, что ручной сценарий на вашей базе уже пройден.
- Автотесты используют изолированную PGlite и не проверяют ваш живой UI.
- Не создавайте новые тестовые записи без отдельного разрешения. Если данных не хватает — отметьте пункт **Заблокировано** и посмотрите раздел «Нужные данные» в `KNOWN_GAPS.md`.
- Middleware кабинетов проверяет cookie сессии, **не роль**. Чужой кабинет может открыться в браузере; мутации должен отвергать сервер. Это отдельный блок чек-листа (права доступа).
- Часовой пояс приложения — `Europe/Moscow`. Даты «сегодня» и «текущий месяц» считайте по Москве.

## Роли и вход

После `start:local` / сида школы `org_school_qa` в боковой панели есть блок **Dev · тестовые аккаунты** (локально демо-вход разрешён). Им можно переключать директора, преподавателей, учеников и Прессу без ручного ввода пароля.

Либо войдите на `/login` существующим email/паролем учебной организации.

Кабинеты:

| Роль membership | Кабинет | Префикс |
|---|---|---|
| `director` | Дирекция | `/direkciya` |
| `teacher` | Кафедра | `/kafedra` |
| `student` | Аудитория | `/auditoria` |
| `press` | Пресса | `/pressa` |

В сайдбаре есть переключатель **Дирекция / Кафедра / Аудитория / Пресса**. Он меняет URL, но не меняет роль сессии. Для проверки чужого кабинета используйте его осознанно (см. `MT` про права).
